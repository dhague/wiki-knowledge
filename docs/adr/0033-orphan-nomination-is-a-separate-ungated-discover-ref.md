# Orphan nomination is a separate, ungated `discover --ref` call

`enchiridion check orphans` reports every page with zero inbound links and names no route forward except deletion. Resolving one is a search problem — *what could link to this?* — and the existing modes answer a different question: they classify a **draft** against the vault under thresholds calibrated for that comparison, and `search` returns the orphan itself ranked first, so a hand-built query reads its own title instead of its neighbours. So `discover` gains a `--ref <page_ref>` mode: it queries with that committed page's own title, summary and body read from `HEAD`, drops the named page and any superseded page, applies **no score gate**, returns the highest-scoring hits capped by `--limit`, emits the existing candidate row with **no `hint`**, and fails rather than printing nothing when the ref is not committed. `wiki-lint` calls it once per `orphans` finding, reads the orphan's body and the bodies of the pages it means to propose through the run's one `read-pages` ledger, and offers a **Resolve orphan page** proposal carrying `{page_ref, blob_oid}` for each.

## Why

- **The repair lands on the linker, not the orphan.** An orphan's problem is the absence of an inbound link, and an edge is directional: a `related:` edge written on the orphan is an outbound link, leaves the inbound count at zero, and changes nothing about the finding. So the proposal names the *candidate* that receives the edge, pointing at the orphan, while the page being repaired is the orphan. Presenting the fix as a property of the orphan would invite exactly the edit that does not work.
- **Nomination is a separate, explicit, index-reading call rather than a new key on the finding row.** The mechanical pass is a working-tree scan that opens no index; the nomination is a `HEAD` read through the search index. Folding candidates into the `orphans` finding would make `check` depend on the index for one check, put a per-finding search cost on every run whether or not anyone resolves an orphan, and blur the two snapshots the procedure deliberately keeps apart — the check's working-tree count and the nomination's committed view. A separate mode keeps the check mechanical and makes the nomination a step whose call, cost and snapshot are visible in the transcript.
- **Nomination is deliberately ungated.** A score threshold is a precision control: it suppresses weak hits to keep a human's review list short. Nomination is a **recall** problem — the failure is missing the page that should carry the link — and the precision comes from the agent reading the orphan's body and the candidate's body before proposing an edge. `discover`'s `related`/`duplicate` thresholds exist to let a draft be classified without a read; this path has a read, so a gate would only hide candidates. The `hint` is omitted for the same reason: it is a classification, and this mode does not classify.
- **`--ref` self-exclusion is inherent, not a flag.** A general `--exclude` belongs on the search surface, where it is a caller's choice with its own semantics; here the named page is structurally the query's own source, so excluding it is part of what the mode means. Putting it on `Query` would make every searcher implement a filter only this caller uses.

## Considered options

- **Teach `check orphans` to open the index and attach candidates to each finding row.** Saves a call, but makes a mechanical working-tree check read committed history, adds a search per orphan to every `check --all`, and reports candidates for orphans nobody is resolving. The two-snapshot split is the reason the check and the nomination must not be one thing.
- **Let the linter build its own `search` query from the orphan's title.** That is the hand-run this replaces: the orphan's own title ranks the orphan first, above anything genuinely related, and the agent has to know to drop it. Measured on a small fixture, a self-title query scored the page 6.27 against 2.87 for a page that genuinely overlaps it.
- **Reuse the draft thresholds and emit a `hint`.** The thresholds compare a draft against the vault; an existing page against the vault is a different comparison, and a `related`/`distinct` verdict the agent then has to override is worse than no verdict.
- **Filter with an `--exclude` field on `Query`.** A second caller would have to agree on what a ref means to the index, and the searcher would grow a filter for one mode. Self-exclusion in the caller leaves the one-method seam untouched.
- **Read the orphan from the working tree.** The index is a view of `HEAD` ([ADR-0015](0015-search-index-view-of-committed-history.md)), so a working-tree read would let the query describe a revision the searcher cannot see; an uncommitted orphan has no committed text to search with, and failing names that instead of returning an empty list.
- **Apply the edge automatically, or batch several candidates into one confirmation.** The type (`related`, or a sharper one the bodies support) is a judgment, and a write without a yes is what the confirm-first rule exists to prevent. One edge per confirmation keeps each yes about one claim.

## Consequences

- `discover` is the one nomination surface, and `--ref` is the one discovery path **with no threshold to recalibrate** when a second search backend arrives: it calls the same one-method `Searcher` seam, applies no score gate, and filters self and superseded rows in the caller. A future backend supplies a second `Searcher` and this path is untouched.
- `--limit` caps the rows, not the scan: the window is a fixed 200 hits, because the rows this mode drops come out of it and the named page ranks its own query first. `--max-candidates`, the gated modes' separate row cap, does not apply here — `--limit 0` is how the lint step takes the whole nomination, so this path does not inherit the silent 15-row truncation that cap would impose.
- The `Hint` vocabulary stays draft-only, and `--ref` rows carry the candidate payload minus `hint`. No new noun names the pages it returns — `Candidate` already means a **Candidate vault** in `CONTEXT.md`, and the row shape is the existing one.
- `check orphans` is unchanged. Its count stays a working-tree read that credits a link from any page, superseded ones included, so it can disagree with the `HEAD` view the candidates come from — an orphan that is not committed clears on commit and cannot be nominated before it; the `--ref` failure names the snapshot rather than implying there are no candidates.
- The linter's evidence rule extends to this check: a proposal cites only bodies this run read, with the `head` and each `blob_oid` from one `read-pages` ledger, never a title, summary, tag, snippet or score.

The proposal shape itself is stated once, in `wiki-lint`'s `reference/proposals.md`: the type is `related` unless the two bodies support a sharper one, one edge per confirmation, and prose that genuinely ought to mention the orphan is named as the sharper **manual** alternative — no subcommand inserts a link at a chosen body position, and the linter has no `Write`, so the command every proposal carries is the frontmatter edge.
