# The wiki title lives in a vault config file and resolves in one place: flag → config → directory name

**Context.** The static export gave every page a sticky nav bar and a front page heading carrying a wiki title, defaulted to the vault root directory name ([ADR-0022](0022-static-html-export.md)) — the one thing a vault calls itself without being told. That default is a filesystem accident: the live dogfooding vault is a directory called `enchiridion-vault`, and a recipient opening an emailed export reads whatever the directory happened to be named rather than what the wiki is about. [#477](https://github.com/dhague/wiki-knowledge/issues/477) makes the title settable — persistently, and overridden for a single run.

**Decision 1 — the saved title lives in `.wiki-knowledge/config.json`, beside the search index.** The export title is *deployment-local presentation state*, not knowledge: it names the wiki to a reader of one exported copy, and it is not something a page should link to, be typed against, tagged with, or be indexed by. Putting it in the vault as content (a committed page, or a frontmatter key on one) would make it all of those things and give it a merge conflict every time the synced vault is edited in two places at once. So it goes where the plugin's other local state already goes — `.wiki-knowledge/`, beside `index.db` ([ADR-0006](0006-stdlib-fts5-not-embeddings.md)) and the ingest/watch locks — a directory `enchiridion init` already gitignores, and which ADR-0006 already requires be excluded from Resilio Sync. The schema today is one optional key, `{"title": string}`, and unknown keys survive a save: `saveExportTitle` reads, merges, writes, so a future key is not silently dropped by a code path that only knows about this one.

**Decision 2 — a missing or broken config is "nothing configured", never an error.** The file is absent until something writes it; `readExportConfig` returns an empty config for an absent file, an unreadable one, malformed JSON, a non-object, and a non-string `title` alike. Each of those means the same thing to every caller — no title was configured — and a title that fails to apply is a cosmetic miss with an obvious next step (run the save again), not a condition worth failing an export over. Degrading to the directory name is also the *safe* direction: for any vault that has a name to fall back to, the resolved title is a real string, and the one root that has none (a filesystem root, whose basename is empty) still lands on the render layer's neutral label rather than an empty nav bar — the last-resort default #476 already established, not a second resolution.

**Decision 3 — the resolution order lives in exactly one function.** `resolveExportTitle(root, flagTitle)` in `enchiridion-ts/src/exportconfig.ts` returns the first of: the per-run flag, the saved `title`, the vault root's directory name. The writer calls it once ([ADR-0022](0022-static-html-export.md)'s "derived in exactly one place" now means this function, which is also the only thing that reads a vault to name one); renderers receive the resolved string and never inspect a vault, and a render pass invoked with no vault at all keeps the neutral `"Wiki"` label from #476. A blank value at either of the first two levels means "not supplied" and falls through — an empty `--title` cannot blank out the nav bar.

**Decision 4 — persistence is a subcommand, not skill-authored JSON.** `enchiridion export --save-title <title>` writes the config and exits, writing no site — persist-and-exit in the shape `--candidates` already uses. The `/wiki-export` skill therefore shells out to save rather than hand-writing JSON, which keeps the file's format, location, and merge behaviour inside the tested helpers, and matches the standing convention that deterministic work is a subcommand (a skill that invented the JSON would be a second, untested writer of the same file). A second full export is deliberately *not* what "save" means here: the skill saves *after* it has already exported, over a target that is now non-empty. A blank title is refused rather than written — "no title" is spelled by not having one, and a stored blank would read back as unset anyway.

## Mechanism

- **New module** `enchiridion-ts/src/exportconfig.ts`: `exportConfigPath`, `readExportConfig`, `writeExportConfig`, `saveExportTitle`, `resolveExportTitle`. Pure filesystem + JSON; no model, no vault reads.
- **`runExport`** takes `opts.title` as the *per-run flag value* and resolves it through `resolveExportTitle(root, opts.title)` — the caller no longer supplies a resolved title, so no caller can invent a different order.
- **The front page's `<h1>`** is the resolved title, not the hardcoded `Wiki` that shipped in #476; the nav bar and the front page heading now name the wiki the same way.
- **CLI surface**: `export --title <title>` (this run only) and `export --save-title <title>` (persist and exit). The save path prints where it wrote and names the title.
- **Skill surface**: `/wiki-export "My Knowledge Base"` passes the positional title through as `--title`, then asks whether to save it as the persistent default and runs `--save-title` on yes.

## Consequences

- Tests split along the same seams as the code: `exportconfig.test.ts` covers the file round-trip, the lenient reads, and the full resolution order without a git repo; the writer tests cover the title reaching the nav bar and heading, and one CLI test covers the skill's two-call flow (save, export, override one run, export again).
- The saved title is vault-local and stays out of git, so two clones of the same vault can carry different titles. That is the intended reading of "deployment-local presentation state" — the export is a rendering of the vault for a reader, and naming it is part of the rendering.
- Nothing but export reads the config today. A second reader is a reason to keep the helper module neutral, which is why `readExportConfig` returns unknown keys rather than a narrowed `{title?}`.

## What would reopen this

The config growing something the *vault itself* must see — a value pages link to, or that ingestion must honour. That is content, and content belongs in the vault and in git; the split this ADR draws is presentation-local versus knowledge, and a key that crosses it reopens the location decision rather than merely extending the file.
