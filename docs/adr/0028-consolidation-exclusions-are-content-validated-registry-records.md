# A declined Consolidation is remembered as a content-validated registry record, and assessed before it is proposed

A `concept-fragmentation` candidate is a lexical cluster, so the user decides whether it really is one concept — and a declined cluster used to be forgotten, so lint proposed the same unchanged pages again on the next run. Two changes together close that loop: every surfaced cluster is first **assessed** from its members' committed bodies and comes back with one disposition (`consolidate`, `relate`, `conflict`) plus a short rationale, and a declined `consolidate` can be **recorded** in a committed `CONSOLIDATION_EXCLUSIONS.yaml` in the cluster's kind-folder, which suppresses that exact member set until one of its members changes meaningfully or a human deletes the record. Assessment is read-only; the registry is written only by `enchiridion exclusion add`; pruning stale records is confirm-first ([ADR-0021](0021-consolidation-is-lossless-delete-not-supersede.md) keeps the Consolidation itself lossless and confirm-first).

## Why

- **A mechanical candidate needs a content-based recommendation before a human can answer it.** Size, inbound links and a lexical similarity score say the pages *look* alike; the disposition says whether they are one concept, two related ones, or two that disagree — three outcomes that need three different repairs, only one of which is a Consolidation. Leaving that read to the ingest flow meant the user first decided whether to hand off, then learned what the merge would be. `wiki-linter` makes the read (on the same model tier as the rest of lint), the human still decides, and `wiki-ingest` still authors the accepted merge.
- **An exclusion must survive an irrelevant edit and expire on a relevant one.** A committed registry keyed on page references alone stops matching the moment a page moves; keyed on raw bytes it expires when YAML is reformatted or a tag is added, and the cluster is proposed again for no reason. So a record caches two facts per member: the blob object ID at `HEAD`, and a **semantic fingerprint** over the decoded `title`, `summary`, typed edges and body — deliberately blind to tags, `source_date`, `volatility`, unrelated keys, field order, YAML formatting and line endings. A matching blob ID is the fast path; a matching fingerprint is the fallback, and `fix consolidation-exclusions` rewrites the cached ID so the fast path comes back.
- **Both facts are materialised by the index pass that already parses every page** ([ADR-0015](0015-search-index-view-of-committed-history.md)). Lint then validates a whole registry from `page` rows — the same HEAD snapshot the cluster was found in — and reparses nothing, which is what keeps a vault full of exclusions cheap to lint. The one thing the index does not carry is conflict edges: `check` parses committed frontmatter for those only once a cluster has survived suppression, so a clean vault pays nothing.
- **The member set identifies the record, and the set it suppresses is the one still standing.** A member that changed meaning leaves the exclusion, so what remains is the record's *effective* set: unchanged members stay excluded while two of them remain, and `fix consolidation-exclusions --prune` offers to drop the rest. A member rejoining, or any other set — a smaller cluster, or a superset once a new near-duplicate joins — is assessed afresh, because the user's "no" was about the pages they saw together. Keeping overlapping records independent means a user can decline `{a,b}`, later see `{b,c}`, and answer that one differently.
- **A `contradicts:` or `supersedes:` edge already settles the pair.** Those pages are related the way they should be — a Consolidation would merge a live conflict or re-open a settled replacement — so the pair is dropped from the candidate set with no registry record and no prompt. That is a fact about the vault, not a decision a user made, which is exactly what distinguishes it from an exclusion.
- **The registry lives in the kind-folder, not in `.wiki-knowledge/`.** A declined cluster is knowledge about the vault's content, so it belongs in the vault's history where it can be reviewed, diffed and reverted; the index is a disposable cache ([ADR-0010](0010-search-index-per-root-cache.md)) and `.wiki-knowledge/` is gitignored. One file per kind-folder follows from a cluster never mixing kinds ([ADR-0027](0027-fragmentation-scope-is-a-declared-allowlist.md)), so a registry is read exactly when its own folder is in scope.
- **Agents must not compute a blob ID or hand-edit YAML.** A hand-written record can pin the wrong revision and silently suppress a cluster whose pages have since diverged — a wrong answer that looks like a clean vault. `exclusion add` captures one HEAD snapshot, verifies it has not moved before committing, and writes canonical YAML; `fix consolidation-exclusions` owns the cache refresh and the confirm-first prune. Humans still inspect and delete records by editing the file, and a malformed file fails open — it suppresses nothing and is reported — because a registry that cannot be read must never hide a proposal.
- **A move is the one page-level event the registry follows.** Within a kind-folder the moved page's reference is rewritten in place; across kinds the member leaves the record under the same fewer-than-two rule, since the cluster is no longer kind-homogeneous.
- **The accepted Consolidation pins the snapshot it was assessed at.** The plan carries `assessed: {head, members: [{page_ref, blob_oid}]}`, and `ingest` refuses it once `HEAD` or a pinned member has moved: the merged body was authored from those exact revisions, so a plan edited or delayed past a commit must be re-assessed rather than merged stale.

## Considered options

- **Keep declining silently** (the status quo). The same cluster returns every run, and the user's judgment is thrown away.
- **Record exclusions in the index only.** Free to maintain and never stale — and destroyed by a rebuild, `--full`, or a clone, so a decision the user made has no durable home.
- **Match on raw content bytes.** Cheapest to compute, and expires on a tag edit, a reformat or a CRLF checkout — the false re-proposal this design exists to remove.
- **Match on the page reference and blob ID alone.** Exact and cheap, but every irrelevant edit resurrects the cluster; the fingerprint is what tells "the page changed" from "the page changed meaning".
- **Suppress by similarity or by a threshold.** Reproduces the mechanical judgment the user was asked for, and would silently swallow a genuinely new cluster that happens to score high.
- **A `supersedes`-style record keeping both pages.** [ADR-0021](0021-consolidation-is-lossless-delete-not-supersede.md) already settled that a Consolidation is a lossless delete; an exclusion is not a relationship between pages at all, it is a decision not to act.
- **A committed allowlist or ignore file per vault.** A list of page refs loses the revision the user actually saw, and grows stale in exactly the way the fingerprint fixes.
- **Compute the fingerprint lazily, at validation time.** Keeps the schema untouched and reparses every page for every registry on every lint run — the cost ADR-0015's materialised view exists to avoid.
- **Have the linter record the exclusion itself, on decline.** A subagent cannot ask for the confirmation that gates a write ([#452](https://github.com/dhague/wiki-knowledge/issues/452)); the invoking session runs the command on an explicit yes.

## Consequences

- **Index schema 6** adds `blob_oid` and `fingerprint` to `page`; a bump drops and rebuilds from `HEAD`, the existing migration strategy.
- `PageChange` gains `oid`, so a HEAD-read consumer can pin a blob without a second git walk.
- `Index.pageFacts(pageRefs)` is the one reader of the cached pair; a page the index does not hold reads as "cannot be read at HEAD".
- Two new subcommands: `enchiridion assess` (the read-only assessment input) and `enchiridion exclusion add` (the one registry write path). `enchiridion fix consolidation-exclusions` gains `--prune` for the confirm-first half, and `FIXES` entries take a `FixOptions`.
- **A new `IngestPlan` feature lands in two places** — `ingest.ts`'s module comment (the schema's only spec) and `wiki-ingest` step 4's agent-facing shape — and `assessed` is a top-level key on the `consolidate` variant only.
- `wiki-lint` gains a step (assess every cluster before judging) and a mechanical check (`consolidation-exclusions`), so the catalogue, its reference and the `wiki-linter` brief all name them; registry integrity reports HIGH.
- **The model tier does not move.** `wiki-linter` stays on the cheap tier: the recommendation is advisory and human-confirmed, while the accepted Consolidation's merged body is still authored on the ingest tier. Escalation waits for a measured eval failure ([#457](https://github.com/dhague/wiki-knowledge/issues/457)).
- Adding an exclusion is one commit of its own, so a declined cluster is recorded even when nothing else is pending; `fix consolidation-exclusions` writes without committing, like every other fix.
- **A stale member is not repaired silently.** It keeps its stale cache so it stays invalid; only `--prune`, after the user agrees, removes it — and deletes a record left with fewer than two valid members.
